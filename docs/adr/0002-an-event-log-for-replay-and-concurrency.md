# ADR 0002：用事件日志保存对局，兼顾回放和并发控制

- 状态：已采纳（v0.2 设计，v0.4 落库，v0.10 用于回放界面）
- 相关：[`architecture.md`](../architecture.md) 第 1.1、4、9.1 节，[`database.md`](../database.md)

## 背景

需要保存对局，并且要满足四件事：

1. 后端重启后，玩家刷新页面能回到同一局。
2. 两个请求同时提交（真人点按钮的同时，后台的 AI 回合也写完了），只能有一个生效。
3. 对局结束后能完整复盘：每一步的局面、每个人当时知道什么、模型为什么这么做。
4. 不同玩家看到的东西不同（保密）。

## 决定

**数据库只存事件，不存“当前状态”。状态由事件按顺序重放得到。**

| 部分 | 做法 |
| --- | --- |
| 事件 | 引擎产生的每个事实（发牌、提名、每张选票、每张任务牌、刺杀）一行，带递增的 `version` |
| 状态 | `replay(events)`；`evolve` 是唯一改变状态的函数，所以重放一定得到同一个状态 |
| 并发 | 每个动作带 `expected_version`；`(game_id, version)` 是主键，后到的写入撞键失败，接口返回 409 |
| 公开记录 | `public_log(events)` 丢掉秘密事件（发牌、单张选票、单张任务牌），给前端逐步播放和 AI 主持用 |
| 模型回合 | 另存 `agent_turns`：模型看到的输入、每次回答、被拒原因、耗时、token，按产生的第一个事件的 `version` 归档 |

## 后果

好处：

- 重启恢复、回放、审计是同一份数据，不需要额外的“快照”或“日志”。
- 回放界面（v0.10）几乎是免费的：前端用公开记录逐步重建桌面，模型回合按 `version` 区间挂到对应的那一步。
- 并发冲突有明确语义：要么写进去，要么 409 让客户端重新拉取，不会出现两个人都以为自己的票算数。
- 测试简单：`replay(stored_events) == live_state` 是一条断言。

代价：

- 每次读取都要重放。一局最多几百个事件，重放在毫秒级，目前不需要快照。
- 新增事件类型时必须同时决定：怎么 `evolve`、要不要进公开记录。漏了公开记录的默认行为是丢弃（宁可少给，不泄密）。
- 事件格式是长期契约；改字段要写迁移或兼容旧格式（`codec.py`）。

## 没有选的方案

| 方案 | 为什么不选 |
| --- | --- |
| 存当前状态（一行 JSON），每次覆盖 | 回放和审计要另做；并发要靠行锁；秘密和公开信息混在一起 |
| 状态 + 单独的操作日志 | 两份数据可能不一致，要额外保证 |
| 事件 + 定期快照 | 现在对局太短，没有必要；以后对局变长再加 |
